# 2026-10-18 延遲與卡住修正

基準是 Render 正在使用的 `1106e7ea4662b2cdada3e4b20a07766cc02abf52`，包含之前的課室恢復修正。改動在 `codex/reduce-game-latency`；正式服務的自動部署關閉，需另行部署才會生效。

## 即時對戰的限制

所有位置、姿勢、攻擊、命中、血量及勝負仍由伺服器的 60Hz 模擬決定。前端沒有加入預測、外推、回滾或提前判定命中。按鍵和觸控事件立即送出，伺服器在真正執行輸入後才回傳狀態，雙方角色直接畫出收到的座標。

改動包括：

- DOM 輸入事件直接送出，不必等下一個渲染／固定更新；快速點按仍由伺服器保留按下邊沿。
- 輸入改變後的第一個伺服器模擬結果立即發送。持續動作的顯示狀態從 20Hz 提至 30Hz，排程保持時間基準，避免 60Hz 計時器的取整令實際頻率降成約 22Hz。
- 移除雙方角色原有的 40ms 指數平滑。這會呈現 30Hz 的已確認座標，沒有另加平滑等待。
- 同一狀態用一次 room union 廣播給兩人，避免重複編碼；保留 volatile 傳輸，擠塞時丟棄過時畫面，結算與退款仍可靠傳送。
- 超過一秒收不到遊戲狀態時，讀取伺服器記憶體內的最新狀態；同步也失敗才重連。此讀取驗證對戰成員，不查資料庫、不推進模擬。
- 狀態序號與 tick 拒絕舊畫面；一般 presence 回覆不會覆寫較新的對戰狀態。
- WebSocket 被網絡封鎖時，Socket.IO 可實際嘗試 polling。Polling 是連線恢復選項，其延遲仍取決於網絡。

## 共用 Node 執行緒與 Supabase

`bcryptjs` 的 Promise API 仍在主執行緒進行密碼計算。原測試的 25 次 cost-10 驗證讓 10ms 心跳最長中斷約 **1,469ms**，足以拖住所有遊戲的計時器。

現在登入、建立帳戶、批次密碼變更使用一個獨立 worker；佇列最多 64 個工作，設有期限及失敗恢復，原有雜湊格式與 cost 10 保持相容。相同本機測試最長心跳間隔約 **23.5ms**，25 次驗證總時間約 1.58 秒。這表示主執行緒恢復運作，並非省掉密碼計算所需的 CPU。

批次匯入先完成密碼計算，再開啟資料庫 transaction，避免等待密碼工作時佔用 Supabase 連線及資料列鎖。部署期間不需 SQL migration，也沒有增加連線池或變更資料庫區域。

已發布的對戰素材目錄在每次服務啟動只解析、補完一次；25 次目錄呼叫的本機耗時由約 **38.7ms → 0.2ms**。找不到 build 時仍會重試，測試切換發布目錄時會重新載入。

## 圖片

貓、狗、豬各有兩張 2048×2048 的舊戰鬥圖集。新招式覆蓋舊招式後，只剩 60 個 256×256 舊姿勢會被引用；現在打包成一張圖，保留所有使用中動作的尺寸、次序、幀數、時間及招式 metadata。384px 的新招式圖集照舊使用。

| 角色舊動作圖集 | 下載前／後，bytes | RGBA 容量前／後 |
| --- | ---: | ---: |
| 星斑貓 | 1,445,718 → 905,620 | 32 → 16 MiB |
| 雲耳狗 | 1,692,492 → 918,534 | 32 → 16 MiB |
| 布丁豬 | 1,386,874 → 769,636 | 32 → 16 MiB |

RGB 採用 quality-98 WebP 再編碼；alpha 逐像素一致。Build 逐像素檢查透明度、平均色差、PSNR、動作映射及下載預算。此版本三個角色的平均 RGB 誤差 0.96–1.12／255，PSNR 41.98–43.52dB。原始美術保留在 public；發布 build 才產生含內容雜湊的 runtime 圖集及相符 manifest。

貓／豬對戰的本機冷載入結果：

- 全部資源傳輸約 **13.49MB → 12.33MB**，減少約 1.16MB。
- 紋理來源的 `寬 × 高 × 4` 容量合計 **167.87MiB → 135.87MiB**，減少 32MiB。這是 RGBA 容量估算，不是實測 Safari／GPU 峰值記憶體。
- 登山遊戲有自有寵物時，不再下載、解碼用不到的 26 張普通登山者動作圖；也移除未使用的 player-idle 圖片請求。

## 卡住與恢復

登山遊戲原本的 `player:join`、`player:question`、`player:answer` 沒有 ack 期限。問題回覆遺失會一直顯示載入中，答案回覆遺失則讓所有選項永久停用。

現在使用六秒 Socket.IO ack 期限並清理 callback。問題重試沿用 request ID，取得相同問題及選項次序；答案沿用伺服器 question ID，從最多 32 筆收據取得結果，避免重複計分、補能量或重設答錯冷卻。正確答案仍只在作答後公開。已開啟的舊版 client 使用 callback-only 問題協議仍可運作。

讀題失敗可重試或返回遊戲；已送出的答案提供同一次提交的重試，等確認後才繼續。斷線會清掉操作，重新加入原房間；外觀相同時保留已載入場景，回到已保存位置、能量及冷卻，並恢復未確認的題目操作。房間已結束／不存在時返回房間選擇，避免留在凍結的遊戲畫面。

Phaser 素材下載限制為同時四個、每次 15 秒、最多重試一次。任何必要素材最終失敗，都會停止建立不完整場景並提供遊戲場景重試；不需整頁 reload。測試覆蓋了實際失敗、重試、場景重新建立及繼續操作。

## 實測與驗證

本機 Chrome，1024×768；同一 WebSocket proxy 每方向加入 0／75／150ms 延遲，每種四次按鍵，量度按鍵到收到伺服器移動狀態：

| 額外模擬 RTT | 原版本 | 修改後 |
| --- | ---: | ---: |
| 0ms | 約 52–99ms | 約 31–48ms |
| 150ms | 約 214–248ms | 約 181–198ms |
| 300ms | 約 364–399ms | 約 335–364ms |

這是短樣本的本機功能比較，不是學校網絡、正式 Render Free 實例或實體 iPad 的延遲保證。網絡來回時間依然要完整等待。

已通過：

- 25 名模擬學生／12 場真實 Socket.IO 同時對戰，每 1.2 秒約 35–36 個顯示狀態；伺服器模擬持續前進；transport 擠塞期間沒有累積舊畫面；結算可靠抵達。
- 截斷狀態後按移動鍵，兩個角色的狀態 tick、座標與畫面座標全部保持不變，確認沒有預測。持續截斷後由伺服器同步恢復，共觀察到六次同步請求。
- WebSocket 被拒仍能連上 polling。
- 真實 HTTP 登入、錯密碼、教師建立學生、批次更改密碼、預設密碼及 cost-10 相容性。
- 遺失讀題／作答 ack 後重試、只計分一次、重連後不用重載場景便可移動、必要圖片失敗及場景重試。
- Chrome／WebKit 54 個介面檢查；桌面、平板及手機 viewport 觸控操作；非實體裝置測試。
- 對戰費用、拒絕、技能、雙方觸控、重連、投降、缺圖取消／退款、排名、平衡、存檔回放與獎勵；PGlite transaction、權限及 rollback。
- `npm run check`、TypeScript 與 production build。CPU 4× 降速的短樣本維持約 60 FPS，沒有超過 100ms 的畫面間隔。

重現入口：

```text
npm run build:pet
npm run check:classroom-performance
npm run check:game-latency-live
npm run check:pet-latency-live
node scripts/test-game-ipad-ui.mjs
node scripts/test-pet-brawl-pvp-live.mjs
```

個別測量與畫面輸出到 `tmp/game-latency`、`tmp/pet-latency`；Playwright 測試使用自己的 JSON fixture，沒有操作正式學生資料。

## 部署仍需處理的項目

Render `Buiosch` 是 Singapore、Free、單一實例，build command 為 `npm install`，會執行包含新圖集打包的 postinstall。Supabase 也在 Singapore；先前審計的連線與查詢時間沒有證據支持搬區或增加連線池。

這批程式修正無法取消 Render 的 Free 閒置規則：[官方文件](https://render.com/docs/free#spinning-down-on-idle) 說明，15 分鐘無入站流量會休眠，再啟動約需一分鐘。本次沒有變更付費方案。對戰儲存在此單一服務的記憶體，部署／重啟會中止進行中的對戰；寵物對戰的既有重啟恢復會退款。應在沒有對戰時部署，然後再量度真實課室 RTT、斷線與伺服器 CPU 情況。
