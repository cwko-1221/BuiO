# 欠交功課無法再儲存：2026-10-20

## 已確認的原因

截圖中的 `Earlier operation needs a retry` 來自瀏覽器的
`shared/reliable-request.js`，不是 Supabase 的錯誤訊息。
舊程式先把完整表格放入 IndexedDB，再依次重送同一學年／班別／科目／日期的較早操作。
一旦較早操作收到 400、403、409 等拒絕，便標為 blocked。之後的儲存遇到它就直接拋出上述錯誤，
即使表格已修正，也不會送到伺服器。「重試」重送的仍是舊表格，沒有使用目前修正的輸入。
例外處理還會把提示改成「等待連線」，掩蓋真正需要修正或核對的狀態。

修正前在獨立測試資料庫重現：功課名稱留空 → HTTP 400 → 補回名稱 →
仍然得到完全相同的 `Earlier operation needs a retry`，無法儲存。
這證實了持續被鎖住的原因；**不能據此斷定該學生最初一定是留空名稱**。

- Render 抽樣紀錄有當天 08:45:47 香港時間的功課 POST 400，伺服器處理約 12 ms。
  15:33:36 及 15:38:38 的功課 GET 約 5 ms。
- Supabase 當天有其他功課建立及修改成功的收據，並有 P5 的已儲存記錄。
  這不能證明每部裝置的網絡一直正常；但持續出現的這句英文確實可在瀏覽器送出新儲存前發生。
- 原日誌只有抽樣狀態碼，沒有最初失敗原因，也沒有該 iPad 的本機佇列，不能把某筆請求歸因到該裝置。
  未修改正式學生功課、監察員權限、Render 計劃或 Supabase 資料。

## 修正

1. 新的明確儲存以完整表格為單位，原子地取代同帳戶／同份功課的過時待送快照。
   舊失敗操作不再攔住修正後的表格；其他類型的提交仍保留原有先後次序。
2. 舊版已卡住的佇列會合併至最新草稿供核對，保留名稱及學生狀態。
   草稿跨重新整理保留；過了 24 小時的功課改為待協助恢復，避免自動刪除。
   跨帳戶不讀取、不重送另一人的草稿；原有登出清除流程不變，因此恢復前不要登出或清除網站資料。
3. 本機先檢查功課名稱及學生狀態；儲存期間避免重複點擊，回應不會蓋掉期間新增的輸入。
4. 同內容重試沿用原有操作識別碼；已提交但回應遺失的操作可由伺服器收據確認，避免重複建立。
5. 已有記錄或版本衝突時，保留輸入、顯示目前已儲存的記錄供核對，再由使用者明確儲存修改。
   更新使用資料庫原子版本條件；相同內容已由背景同步完成的情況可正常確認。
   舊版沒有版本資料的待更新操作須先核對，不自動覆蓋其他人的記錄。
6. 修正切換科目時選單的數字／字串 ID 比較；新科目載入期間隱藏舊表格，避免輸入被後到的讀取結果蓋掉。
   背景重試不再阻塞整個模組開啟。
7. 每次功課儲存被拒會記錄固定診斷代碼及 request ID，不記錄學生姓名、答案、狀態表格或密碼。

## 受影響裝置的恢復

先截圖備份現有表格，再在**同一部 iPad、同一個科長帳戶**重新整理欠交功課頁。
找到還原的草稿，核對科目、日期、功課名稱及各人狀態後儲存。
如果伺服器已有另一版本，先展開「查看目前已儲存的記錄作核對」。
不要清除 Safari 網站資料、使用登出來排錯，或把另一部裝置當成能讀取這部 iPad 的草稿。
過往日期仍需由老師依畫面草稿協助補錄，不放寬科長的日期或班別權限。
